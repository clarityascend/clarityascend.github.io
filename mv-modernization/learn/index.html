MultiValue, explained simply.

Many banks, insurers, distributors and public bodies still run on MultiValue databases such as UniVerse and UniData. This guide shows how they work in plain words, and how modern tools make them easier to learn.

One idea to remember

A field can hold a list, not just one value.

Name[Customer name]
Phones[Home][Mobile][Work]
City[City]

In a classic SQL database, those three phones would usually need a second table.

Fields, values and sub-values

A MultiValue record is like a set of nested boxes. Our logo shows it: one slice for a field, three for its values, five for the sub-values inside them.

^

Field

One piece of information, like a column. Also called an attribute. Separated by a field mark (@FM).

]

Value

One item in a field's list, like each phone number. Separated by a value mark (@VM).

\

Sub-value

A list inside a value, like extensions for one work number. Separated by a sub-value mark (@SM).

[Name]^[Home]][Mobile]][Work]^[City]

How the record above looks when typed in MVBU, using ^ ] \ for the three marks.

Eight words you'll hear on day one

File
A collection of records, roughly a table.
Record & key
One entry in a file, found by its unique key (the record ID).
Dictionary
Describes a file's fields: names, positions, formats.
TCL / ECL
The command line of UniVerse (TCL) and UniData (ECL).
LIST & SORT
English-like query commands that print reports.
Select list
A saved list of record keys that the next command works on.
BASIC program
The business logic, written in MultiValue BASIC.
Subroutine
A reusable BASIC program others CALL, often acting as an API.

Your first query, word by word

MultiValue queries read almost like English. Here is one that lists London customers by name.

LIST CUSTOMERS WITH CITY = "London" NAME BALANCE

Why "modernize"?

The database is usually fine. What gets old is the way people reach it: small terminal windows and code few people remember writing. Modernizing means better windows and better maps, not starting over.
